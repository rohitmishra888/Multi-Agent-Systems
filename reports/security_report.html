VAmPI's email update endpoint is documented as containing SQL injection. Automated error signatures were not detected (VAmPI may swallow errors), but manual testing with UNION-based payloads is recommended.

CRITICAL CONFIRMED MASS-001 — Mass Assignment — Admin Privilege Escalation via Registration 9.8 ▼
OWASP Category
API6:2019 Mass Assignment
Endpoint
POST /users/v1/register
CVSS v3.1
9.8 CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H
Description
The registration endpoint accepted the extra field(s) {"admin": true} and applied them to the user's account. The user 'mass_105e0f2b' was registered with admin privileges by including {"admin": true} in the registration payload.
Impact
Any unauthenticated user can self-register as an administrator, gaining full administrative access to the application.

HTTP Evidence

MethodURLStatus
POST http://localhost:5000/users/v1/register 200
GET http://localhost:5000/me 200

Proof of Concept

curl -X POST http://localhost:5000/users/v1/register \
  -H 'Content-Type: application/json' \
  -d '{"username": "hacker", "password": "pass", "email": "h@x.com", "admin": true}'
# Then login as 'hacker' — admin=true confirmed in profile

Remediation

  • Use a whitelist of allowed registration fields: only username, email, password.
  • Never bind request body directly to the user model/ORM object.
  • Implement explicit field assignment instead of bulk update patterns.
  • Validate and reject any extra fields not in the allowed whitelist.
  • Use a dedicated registration DTO that excludes admin/role fields.

HIGH CONFIRMED BOLA-001 — Broken Object Level Authorization — Cross-User Profile Read 8.1 ▼
OWASP Category
API1:2019 Broken Object Level Authorization
Endpoint
GET /users/v1/{username}
CVSS v3.1
8.1 CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N
Description
User 'bola_a_2ffba4' (authenticated with their own JWT) successfully accessed User 'bola_b_2ffba4's profile data by simply changing the username in the URL. The API does not verify that the requesting user owns the resource.
Impact
Any authenticated user can read any other user's profile data, including potentially sensitive fields like email addresses and admin flags.

HTTP Evidence

MethodURLStatus
GET http://localhost:5000/users/v1/bola_b_2ffba4 200

Proof of Concept

# Login as User A to get JWT
curl -X POST http://localhost:5000/users/v1/login -d '{"username":"bola_a_2ffba4","password":"..."}'

# Use User A's JWT to access User B's data
curl -H 'Authorization: Bearer <JWT_A>' http://localhost:5000/users/v1/bola_b_2ffba4

Remediation

  • Verify that the authenticated user ID matches the requested resource owner ID.
  • Use the JWT sub/username claim to authorise resource access, not the URL parameter.
  • Implement object-level access control checks in every endpoint handler.
  • Return HTTP 403 Forbidden when a user attempts to access another user's resource.

MEDIUM CONFIRMED RATE-001 — No Rate Limiting on Registration Endpoint — Account Creation Spam 5.3 ▼
OWASP Category
API4:2019 Lack of Resources & Rate Limiting
Endpoint
POST /users/v1/register
CVSS v3.1
5.3 CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L
Description
Successfully registered 10 accounts in rapid succession without any rate limiting. All requests returned success status codes.
Impact
Attackers can create unlimited accounts (bot registration, spam, resource exhaustion of database and storage).

Proof of Concept

for i in range(1000):
    requests.post('http://localhost:5000/users/v1/register',
        json={"username":f"spam{i}","password":"x","email":f"s{i}@x.com"})

Remediation

  • Implement IP-based rate limiting on registration (max 5/hour per IP).
  • Add email verification to prevent disposable email spam.
  • Implement CAPTCHA on registration.
  • Return HTTP 429 with Retry-After when limit exceeded.
